# Guarantees and boundaries

The local acceptance suite exercised these contracts as recorded in [acceptance evidence](acceptance.md). Limits remain explicit.

1. **Delivery:** Kafka transports records; Flink checkpoints every 10 seconds with a 60-second timeout and bounded restart policy. JDBC and audit Kafka sinks are at-least-once. The system is not end-to-end exactly-once. Kafka source offsets are committed after completed checkpoints; normal TaskManager recovery restores the JobManager's checkpoint. JobManager loss requires explicit resubmission from a retained checkpoint (no HA coordinator is configured).
2. **Canonical identity:** PostgreSQL primary key is `(namespace,run_id,event_id)`. INSERT ON CONFLICT DO NOTHING protects results beyond the 24-hour Flink event-ID state TTL, including older checkpoint restoration and repeated JDBC writes. First accepted payload wins. Conflicting payloads under the same identity are outside the trusted simulator contract, not silently considered valid new events.
3. **Ordering:** match/gameplay partition by match, session/server by server, each within a topic. Cross-topic ordering is never assumed. The source decoder retains Kafka topic, partition, offset and ingress wall time. Wire source timestamps drive per-partition watermarks; invalid timestamps do not advance them. Idle source partitions are excluded after 15 seconds. Timezone-bearing timestamps are parsed as instants; producers emit UTC.
4. **Lateness:** default watermark tolerance 10 seconds. Events older than watermark minus 60 seconds are persisted with `excessively_late=true` and written to the late audit topic. Curated views exclude them until idempotent reconciliation sets corrected_at. Within-policy events affect canonical views immediately. After reconciliation, affected matches/windows show corrected. Server windows remain provisional without a source completeness manifest. Flink's server-window observation sink is diagnostic; canonical SQL windows are the source of analytical truth.
5. **Revisions:** immutable facts avoid stale aggregate overwrite. Sessions choose maximum sequence per namespace/run/server/player/session. Diagnostic window counts use greatest(previous,new), never an additive retry; they can undercount after window expiry and are not canonical metrics. No changing leaderboard aggregate is blindly overwritten from an older checkpoint.
6. **Completeness:** match status requires a created roster, final manifest, exact declared gameplay event identities/count/sequence max and matching per-player kills/damage/placement. A finish-first event cannot freeze an incomplete result. Running or unmatched outcomes are provisional; one query sees a consistent PostgreSQL statement snapshot. Multiple independent dashboard queries may observe slightly different commit states. Manifest expected counts cover gameplay only; sessions/server cadence completion is checked separately by smoke tests, not falsely certified by match finality.
7. **Sink consistency:** raw events, rejection rows, Kafka audit topics and window observations are separate sinks and not atomic as a group. JDBC batch flush/retries and checkpoints provide eventual propagation, not cross-sink transactions. Batch export uses repeatable read across all CSVs. No retried `kills=kills+1` exists.
8. **Simulation:** Match domain actions preserve alive/health/outcome invariants. Each delivery retry keeps its identity; duplicates do not re-run domain actions. Independent source loops own separate Kafka producer clients and RNGs. The seeded domain outcome and logical gameplay sequence are reproducible; UTC timestamps and operational source interleaving are wall-clock dependent. Do not promise byte-identical multi-source traces. A producer process restart starts a genuinely new run; in-memory simulation state is not a recoverable authoritative production service. Never reuse RUN_ID to restart a partially emitted simulation. Replay preserves source run, event ID and event time in a new namespace; emitted_at records replay delivery time.
9. **Retention:** single-broker Kafka has six-hour / per-partition byte limits; no HA. A Docker named volume is only development persistence, not durable cloud storage. Raw PostgreSQL data is not automatically deleted; archives are explicitly bounded to 100000 rows per chosen run. Workspace deletion loses volumes unless independently preserved. Do not restore a checkpoint whose needed Kafka offsets have expired and claim a lossless recovery.
10. **Availability/security:** Compose publishes only loopback admin ports; PostgreSQL/Kafka are not host-published. Keep Codespaces forwards private. Admin actions are CLI-only; no public mutable web endpoint or Docker socket mounted into an app. Superset uses the legacy-named `tableau_reader` role, which only reads mart views. No budgeted resources or trials are provisioned.

Remaining limits: no source payload conflict audit, producer process state recovery, automatic JobManager HA, production security review or sustained-load certification. Superset replaces the unavailable Tableau authoring route; retained Tableau specifications are optional references.
